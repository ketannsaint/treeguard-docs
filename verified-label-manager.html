What was measured

The run used a disposable company-managed Jira project and the same REST operations used by the Forge client. It created 2,000 fixture issues, applied a label change in two 1,000-issue bulk tasks, verified every issue, reversed the change, and deleted the project.

Phase Result
Fixture creation 830.4 seconds, 40 batches of 50
Search 4.2 seconds, 20 pages of 100
Bulk add 0.50 / 0.47 seconds to submit; 272 / 252 seconds to complete
Bulk remove 0.65 / 0.41 seconds to submit; 264 / 270 seconds to complete
Verification 3.8 seconds; 2,000 / 2,000 correct
Reverse operation 1,056 seconds; exact original labels restored

Why the queue exists

Submitting a Jira bulk task took less than a second. Processing a 1,000-issue task took 250-272 seconds. That is far beyond Forge's 25-second invocation limit, so the app submits, polls, and records progress through an asynchronous queue instead of pretending the edit is synchronous.

Two defects found before release

The live boundary test found two defects that the 100-test unit suite could not reach. Both were fixed and re-verified before this report was written.

  • The queue consumer used the deprecated event contract for the installed events package. A run failed at queue submission; the manifest and handler now use the current contract.
  • Journal integrity depended on object key order surviving a Forge KVS round trip. The digest now canonicalizes nested object keys, and a reordering regression test covers the platform behavior.

What this does and does not establish

Established

  • Exact label changes at 2,000 issues.
  • Unrelated labels survived the forward operation.
  • The reverse pass restored every original label set.
  • Jira did not rate-limit the measured five-second polls.

Still bounded

  • Each operation is limited to 2,000 issues.
  • The operator needs Administer Jira and Make bulk changes.
  • Undo is compensation, not a transactional database rollback.
  • A label with no issues cannot be deleted through Jira's API.

Not claimed here

  • That every permission or licensing path is live-tested.
  • That inaccessible issues can be changed or recovered.
  • That the app is available for general Marketplace install.
  • That this one run predicts a customer's exact runtime.
